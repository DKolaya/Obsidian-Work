# ORDA Positive Pay

## Background

- Toolkit apps: single application, multiple modules, each doing an import (or in this case, export) for a customer. Core logic generally shared across customers; variation is per-customer business logic/validation and file format.
- Manual imports = multi-step UI (upload file → validate → push to Intacct). Positive Pay is the odd one out: it's an **export**, not import.
- Positive Pay (bank process): checks deposited via desktop/remote scanner (not at a bank branch) need a secondary verification file sent to the bank — list of check numbers/info confirming which checks were completed. Separate channel from the funds deposit itself.
- Our part: look for checks in Intacct and build the export file the bank expects.
- Customer: ORDA (contact rgraham@orda.org). Prep material: "FW: ORDA - Positive Pay" email forwarded by Patrick, 2026-07-21.
- Reference project: CSAC (existing toolkit implementation) — to review alongside for comparison/pattern while building this one.

## Scope framing

- Not built from scratch — reusing existing toolkit system, doing "the last 10-20%" of customization for ORDA.
- No hard deadline. Patrick confirmed there's time; earlier "one week" mention was a casual ballpark, not a real target.

## Core Toolkit — Deferred Improvements

Found while consolidating the Positive Pay app layer into `Core_PositivePay` (2026-08-11, see status log). **Deliberately not fixed** in that pass — it was scoped behavior-neutral so no migrations were needed in either customer app. These need a team decision before anyone touches them. Bank file spec context: [[06_Resources/KeyBank/KeyBank ARP and Positive Pay Toolkit]].

**Correctness**

- **Void detection is a substring heuristic.** `IsVoid = DOCNUMBER.Contains("Void", OrdinalIgnoreCase)`. Present in **both** ORDA and CSAC (now shared in `PositivePayExportServiceBase.CreateExportCheck`). `APPayment.STATE` carries the real void status and is already synced and indexed. A vendor legitimately named e.g. "VOID SERVICES LLC" would be flagged void on a live bank file — for KeyBank that sets the void character to `C`, telling the bank to stop paying a check that is actually good. Highest-priority item on this list.
- **No explicit ordering of export rows** — the void/cancel-before-issue bug found in the 2026-08-11 review (check numbers `33567`, `33554`). Now shared: `PositivePayExportServiceBase.Export` hands `exportBatch.Checks` to the formatter in whatever order EF returned them. Still needs the business decision on same-batch void semantics (net out vs. ordered pair) before a fix, but note the fix now lands in **one** place for all customers instead of two.
- **`ExportCheck.PayeeName` is capped at 100 chars, KeyBank PNV allows 150** (2 × 75-char lines). The export-time splitter can fill both lines, but the column truncates upstream, so a long payee name is already lost before it reaches the formatter. Needs a migration in both repos.

**Error handling / contracts**

- **`PositivePayExportResult` has no success or error surface** — `FileName`/`ContentType`/`Content` only, unlike `Core_Contracts/Result/AbstractResult.cs` that the import side uses. A field-width violation surfaces only as a thrown `InvalidOperationException` caught by a Razor try/catch into a snackbar. The export correctly aborts before any DB write, but the user gets a toast, not a structured per-row report of which check failed.
- **`SyncAPPaymentsAsync` returns bare `Task`** — no added/updated counts, asymmetric with `SyncMetadataAsync`'s `PositivePayMetadataSyncResult`. The counts are already computed and logged, just not returned.
- ~~**`IExportBatch` omits `IntacctEntityId`, `ExportedBy`, `BatchName`** that the concrete `ExportBatch<T>` carries, so pages coding against the interface can't reach them.~~ **Fixed 2026-08-11** — the frontend abstraction forced it: the shared history grid reads `BatchName` and `ExportedBy`, and once the page went through `IExportBatch` it couldn't see them. Added all three to the interface; `ExportBatch<T>` already implemented them, so it is interface-only with no schema change.
- **`Export()` is the only non-`Async`-suffixed member** of `IPositivePayExportService`.

**Schema / project hygiene**

- **`ExportedBy` has no `[MaxLength]`** on either `ExportBatch` or `ExportFileBytes` → `nvarchar(max)`.
- **`Core_PositivePay.csproj` targets `net8.0` with EF Core 9.0.14 packages.**
- **CSAC has no design-time `DbContextFactory`**, so `dotnet ef` there requires a reachable SQL Server. ORDA has one (`PositivePay/DAL/PositivePayContextFactory.cs`) — CSAC should get the equivalent.

**UI**

- **CSAC's default-account logic overwrites the user's pick on every sync** (`Export.razor`, hardcoded to "MT Bank Operating" / "39900157"). ORDA already fixed this by only re-defaulting when the selection is unset or invalid. The fix should follow the service consolidation into CSAC. Overlaps Nathan's unmerged `origin/improvement/PositivePay-consistency` branch — coordinate before editing those pages.

**Testability (already known, repeated for completeness)**

- **`Core_Intacct.IntacctClient` is `sealed` with non-virtual methods** so it can't be mocked. This blocked sync-service tests for ORDA (logged 2026-08-06) and now blocks testing the *shared* `PositivePaySyncServiceBase`, which raises the value of fixing it — one interface extraction would unblock sync tests for every customer app at once.

**Repo sharing model** — *(corrected 2026-08-11; the earlier claim here that these were "not forks in any technical sense" was wrong. It was inferred from `git remote -v` showing only `origin` and no `upstream`, but fork status is a GitHub-server-side property that git itself has no concept of, so local remotes prove nothing about it.)*

They **are** real GitHub forks: `gh repo view` reports `isFork=true` on both `CSAC_Intacct_Toolkit` and `ORDA_Intacct_Toolkit` with `parent=CDHTS/Intacct_Toolkit_Core` (`forkCount=2`), and all three share root commit `fcaec0c`. CSAC's history also carries ~20 `Merge remote-tracking branch 'upstream/master'` commits between 2026-04-28 and 2026-05-22, so the fork workflow was actively used and then abandoned — the `upstream` remote is gone from the current clone, and that is exactly when drift started.

State as of 2026-08-11: ORDA's `master` is *exactly* Core's `master` (`4e809c6`, zero drift). CSAC is 3 commits behind and has 32 commits touching `Core_*` since diverging; CSAC's `master` is not in Core and Core's `master` is not in CSAC, because Core absorbed CSAC's improvements by hand-copy (`f1070bf`) rather than by merge. Content converged, history did not.

**Recommendation: stay on forks, skip NuGet for now.** Withholding a fork sync already *is* a version pin, which was the main thing NuGet would have bought. With no CI and manual on-prem deploys, `dotnet pack`/`push` just replaces one manual step with another, and it penalises this team's actual working pattern — `Core_Components` has 10 commits in Core against 15 in CSAC, i.e. Core improvements get discovered while building customer features, which is precisely what a package boundary makes harder (no in-place edit, no F12 into Core).

What forks actually lack is **version identity**, and Core has **zero tags** today (CSAC already tags its own deployments — `v1.0`, `deployment-prep/v1.1` — so the habit exists, it was just never applied to Core). Four cheap fixes close the gap:

1. Tag Core releases (`v1.2.0`) and merge the *tag* into a fork, never `master`.
2. Record the Core version in each fork (`<CoreVersion>` property or a `CORE_VERSION` file) so it is greppable.
3. Restore the `upstream` remote in both clones.
4. Upstream flow: PR from fork → Core (GitHub supports fork→parent natively). Core-first is ideal but loses to momentum; periodic reconciliation is what produced `f1070bf` in the first place.

**Monorepo: rejected.** Nothing contractual forces separate repos — it is convention — but a monorepo puts every app on one Core commit, so a Core change must be fixed everywhere at once. That contradicts the requirement to upgrade clients on their own schedule.

**Revisit NuGet when** CI exists to pack/push automatically, a fourth customer app appears, or Core stops changing often enough that in-place editing stops mattering.

**One-time cleanup:** reconcile CSAC and Core once via `upstream` (the content is already identical) so future syncs are clean rather than whole-tree merges.
